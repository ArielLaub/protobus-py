## Install

The CLI ships with protobus — `pip install protobus` puts a `protobus` command
on your path. There is no `protoc` to install: the `.proto` files are parsed by
the library itself.

```bash
pip install protobus
protobus --help
```

If the command is not on your path (a virtualenv that is not activated, say),
`python -m protobus.cli.main` is the same entry point.

## Commands

### `protobus generate`

Generates Python typing from all `.proto` files in your proto directory.

```bash
protobus generate
```

**What it does:**
1. Finds all `.proto` files under your configured `proto_dir`, recursively
2. Parses them, in dependency order, with the same parser the runtime uses
3. Writes one module to `types_output` containing, for every service:
   - a `<SERVICE>_NAME` constant with the full service name
   - a `typing.Protocol` whose method signatures are exactly what `ServiceProxy` installs
   - a `TypedDict` per message the service's methods use, transitively
   - a `Literal[...]` of value names per enum

**Output example.** Given `proto/Calculator.proto`:

```protobuf
syntax = "proto3";
package Calculator;

service Service {
  rpc add(AddRequest) returns (AddResponse);
}

message AddRequest {
  int32 a = 1;
  int32 b = 2;
}

message AddResponse {
  int32 result = 1;
}
```

it writes `types/proto.py`:

```python
# Auto-generated by protobus CLI - do not edit manually
from typing import AsyncIterator, Dict, List, Optional, Protocol, TypedDict
from protobus import CallOptions, StreamOptions


SERVICE_NAME = "Calculator.Service"

class Service(Protocol):
    async def add(self, request: "AddRequest", actor: Optional[str] = None, rpc: bool = True, timeout_ms: Optional[int] = None, options: Optional[CallOptions] = None) -> "AddResponse": ...

class AddRequest(TypedDict, total=False):
    a: int
    b: int

class AddResponse(TypedDict, total=False):
    result: int
```

The pieces worth knowing:

| Generated | What it is for |
|---|---|
| `SERVICE_NAME` | the string to pass to `ServiceProxy` and to set as `service_name`. Use it rather than a literal |
| `Service` | the `Protocol` to annotate a proxy with — `calculator: Service = ServiceProxy(context, SERVICE_NAME)` — so a misnamed rpc or a wrong request shape is a type-checker error at the call site |
| `AddRequest` / `AddResponse` | the request and response shapes — `total=False`, because proto3 has no required fields |
| the method signature | `(request, actor=None, rpc=True, timeout_ms=None, options=None)` for a unary method; `(request, actor=None, idle_timeout_ms=None, options=None)` returning `AsyncIterator[...]` for a server-streaming one |

Field typing follows the [decoding rules](../guide/schema.md#what-a-decoded-message-looks-like): 64-bit integers are `int`, `bytes` is `bytes`, a message field is `Optional[...]`, `repeated` is `List[...]`, a map is `Dict[...]`, an enum is a `Literal` of its value names, and a custom type is whatever its `py_type` says (`datetime` for `timestamp`, `int` for `bigint`).

**Several packages.** When the services in `proto_dir` come from one package, names are emitted as above. When they span several, every name keeps its package as a prefix — `ORDERS_SERVICE_NAME`, `Orders_Service`, `Orders_AddRequest` — because the output is a single module and two packages may well both declare a `Request`.

### `protobus generate:service <Name>`

Generates a service stub that implements all RPC methods from a `.proto` file.

```bash
protobus generate:service Calculator
```

**What it does:**
1. Reads `<Name>.proto` from your `proto_dir`
2. Parses the service definition and RPC methods
3. Generates a Python class extending `RunnableService`, with one method per rpc (an async generator for a streaming rpc)
4. Creates the file at `services_dir/<name>/<name>_service.py`

**Output example:**

Generates `services/calculator/calculator_service.py`:

```python
"""
Calculator.Service implementation.

Generated by protobus CLI. Implement the methods below.
"""

import asyncio
import os

from protobus import Context, MessageHandlerContext, RunnableService


class CalculatorService(RunnableService):
    service_name = "Calculator.Service"

    async def add(self, request: dict, actor: str, correlation_id: str) -> dict:
        """AddRequest -> AddResponse."""
        raise NotImplementedError("add")


async def main() -> None:
    context = Context()
    await context.init(
        os.environ.get("AMQP_URL", "amqp://guest:guest@localhost:5672/"),
        [os.environ.get("PROTO_PATH", "./proto")],
    )
    await CalculatorService.start(context)


if __name__ == "__main__":
    asyncio.run(main())
```

The generator refuses to overwrite: running it again fails with
`Service file already exists: … Remove it first if you want to regenerate.`
A `.proto` that does not exist fails with `Proto file not found: …`, and a
`<Name>` that is not a plain identifier is refused before any path is built.

## Configuration

Configure the CLI by adding a `[tool.protobus]` table to your `pyproject.toml`:

```toml
[tool.protobus]
proto_dir = "./proto"
types_output = "./types/proto.py"
services_dir = "./services"
```

### Configuration Options

| Option | Default | Description |
|--------|---------|-------------|
| `proto_dir` | `./proto` | Directory containing `.proto` files |
| `types_output` | `./types/proto.py` | Output path for generated typing |
| `services_dir` | `./services` | Directory for generated service stubs |

Paths are relative to the directory holding `pyproject.toml`. The TypeScript
port's camelCase spellings (`protoDir`, `typesOutput`, `servicesDir`) are
accepted too. On Python 3.10 the `tomli` package is used to read the file; it
is installed as a dependency automatically.

## Project Structure

The CLI expects and generates the following structure:

```
my-project/
├── proto/                      # .proto files
│   ├── Calculator.proto
│   └── Notifications.proto
├── types/
│   └── proto.py                # Generated typing (by protobus generate)
├── services/
│   ├── calculator/
│   │   └── calculator_service.py   # Generated stub (by protobus generate:service)
│   └── notifications/
│       └── notifications_service.py
├── pyproject.toml
└── docker-compose.yml
```

## Workflow

The typical development workflow with the CLI:

1. **Create a proto file:**
   ```bash
   vim proto/Calculator.proto
   ```

2. **Generate typing:**
   ```bash
   protobus generate
   ```

3. **Generate service stub:**
   ```bash
   protobus generate:service Calculator
   ```

4. **Implement the service:**
   Open `services/calculator/calculator_service.py` and replace the `NotImplementedError`s. Annotate the methods with the generated `TypedDict`s if you want them checked:
   ```python
   from types.proto import AddRequest, AddResponse

   async def add(self, request: AddRequest, actor: str, correlation_id: str) -> AddResponse:
       return {"result": request["a"] + request["b"]}
   ```

5. **Run the service:**
   ```bash
   python services/calculator/calculator_service.py
   ```

## Tips

- Run `protobus generate` as part of your build or pre-commit so the typing never drifts from the schema
- The service generator will not overwrite existing files - delete the file first if you want to regenerate
- Use the `SERVICE_NAME` constant instead of hardcoding strings
- `mypy` and `pyright` both understand `TypedDict` and `Protocol`; a proxy annotated with the generated `Protocol` gets its methods checked, an unannotated one is `Any`
